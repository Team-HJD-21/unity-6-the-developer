## 프로젝트 한 줄 소개

외계 생명체의 웨이브로부터 제어 장치를 방어하는 탑다운 호드 모드/타워 디펜스 게임입니다.
우주선을 메인 허브로 삼아 연구·장비·스테이지를 선택하고, 행성에서 확장형 웨이브 디펜스를 진행합니다.
싱글플레이 성장과 2인 협동을 연결하고, 장래에는 SOS 구조 요청, 랜덤 매칭, 리더보드, PvP 확장까지 고려합니다.

## 우리가 만들 게임

### 메인 허브: 우주선과 다이아제틱 UI

- 단순 메뉴가 아니라 탑다운 우주선 내부를 돌아다니며 기능을 선택합니다.
- 연구소를 누르면 무기 연구 화면으로, 조종석을 누르면 HUD/홀로그램 스타일의 행성 선택 화면으로 전환합니다.
- UI는 “메뉴를 연다”보다 플레이어가 우주선의 장치를 사용한다는 감각을 목표로 합니다.

### 스토리/전투

- 행성별 스테이지에서 웨이브를 돌파하는 탑다운 액션 + 터렛 디펜스.
- 선봉대가 남긴 캐논/미사일 터렛을 활용하고, 제어 장치의 총 전력량 안에서 전략적으로 켜고 끕니다.
- 플레이어는 직접 사격으로 터렛의 사각지대를 지키고, 적을 유인해 방어선을 유지합니다.
- 기본/탱커/원거리/암살자 계열의 적 조합과 최종 웨이브 보스가 전투의 핵심입니다.
- 스테이지를 진행하면서 터렛 설치·통제 가능 영역이 확장됩니다.
- 날씨, 시간대, 중력 등 행성별 환경 변수를 전투 기믹으로 활용합니다.
- 실패해도 플레이 전체가 무너지지 않도록, 감소된 비율의 재화를 지급합니다.

### 성장과 경제

- Player: 체력, 방어력, 회피율 등 스킬 트리형 연구.
- Weapon/Turret: 별도 연구 카테고리.
- Control Unit: 전력 확장과 위험/보상 요소를 가진 성장 축.
- 스테이지·미니게임·협동에서 얻는 재화와 해금은 하나의 계정 Profile에 축적됩니다.
- 재화·해금·연구는 백엔드 검증을 목표로 하며, 로컬 Binary 데이터는 캐시/복구 목적입니다.

### 온라인 협동과 장래 확장

- Steam 기반의 온라인 계정, 친구 초대, 랜덤 매칭을 목표로 합니다.
- 우선 목표는 2인 협동입니다.
- 참가자 연결이 끊기면 재접속을 지원하고, 필요 시 Ally AI가 플레이어 슬롯을 이어받습니다.
- Host Migration, 채팅, 미니맵 Ping, SOS 구조 요청은 온라인 확장 기능으로 설계합니다.
- PvP는 Deferred입니다. 지금은 PvE/협동의 코어를 만들되, 나중에 확장할 수 있는 권한·모드 규칙 구조를 준비합니다.

## 현재 상황과 개발 방식

기존 Unity 프로젝트는 Unity 6로 올라와 있으며, 플레이어·몬스터·터렛·스테이지·UI 리소스와 레거시
게임플레이 구현이 존재합니다. 다만 기존 Manager/Singleton/static 구조는 Steam 온라인, 공유 Profile,
협동, Host Migration까지 확장하기에 적합하지 않습니다.

그래서 프로젝트를 통째로 폐기하지 않습니다. 기존 콘텐츠와 동작을 레퍼런스로 유지하면서,
새 시스템 코어를 병렬로 구축하고 기능 단위로 교체합니다.

> 프로젝트의 원형은 2024년 수업 프로젝트로 개발된 The Developer입니다. Steam 출시를 목표로 전환하면서
> 기존 콘텐츠와 외부 에셋의 상업 사용 권리는 별도 감사 및 교체 대상으로 관리합니다.

> 영상 티저 : https://www.youtube.com/watch?v=wm4V9DZsgH8
> 기존 플레이 영상 : https://youtu.be/CM-05SvCNTQ?si=l3xWrRBCS84fWp5h

### 상업 출시 목표

- 팀은 사업자 기반을 갖추고 Steam 출시를 전제로 프로젝트를 운영합니다.
- 출시 가능한 빌드, Steam 상점 페이지/배포 준비, 상업 에셋 권리 정리, 사용자 피드백과 운영 기반을 목표로 합니다.
- 합류 전에는 역할 범위, 기여물 권리, 수익 발생 시의 정산 원칙 등 상업 프로젝트에 필요한 조건을 문서로 투명하게 공유합니다.

```text
Legacy 콘텐츠/프리팹/연출
        ↓ 레퍼런스 및 점진 이식
New Core
  Bootstrap / Profile / Content / MatchSession / GameSimulation
        ↓
Single Story Vertical Slice
        ↓
2-player Coop + Online Services
```

## 기술 방향

- Engine: Unity 6, C#
- Core architecture: Bootstrap / Domain / Application / Infrastructure / Presentation
- 게임 규칙: `MatchSession`, `MatchState`, `GameSimulation`, `ModeRules`
- 콘텐츠/밸런스: versioned `Definition`과 `ContentCatalog`
- 성장/경제: backend-authoritative `PlayerProfile`, local binary cache
- UI: 상태·이벤트를 구독하는 Presenter 구조
- 멀티플레이: Steam identity, Lobby/Matchmaking, future network authority/host migration
- 테스트: Main/Singleton 없이 동작하는 최소 Test Scene 및 EditMode 테스트

새 기능은 기존 `GeneralManager`, `GameManager`, `DataManager`, `InGameManager`에 추가하지 않습니다.
레거시는 참고하고, 새 Core에 기능을 하나씩 재구현·이식합니다.

## 모집 역할

현재 기획과 시스템 설계가 마무리되는 과정이므로, **최종 역할 분배는 아직 확정되지 않았습니다.**
아래는 현재 필요한 업무 영역의 예시입니다. 합류 후 확정된 기획, 각자의 관심 영역, 실제 확보 시간,
기존 팀 구성에 맞춰 역할 범위와 기능 단위를 함께 조율합니다.

역할은 한 사람이 모든 것을 떠안는 방식이 아니라, 담당 영역의 **기능 완결성**을 책임지는 방식입니다.
숙련도보다 약속한 시간, 피드백 수용, 문서화와 마무리 능력을 중요하게 봅니다.

## 우리가 중요하게 보는 협업 원칙

### 1. 공과 사의 분리

친해도 작업 기준은 분명하게 둡니다. 개인 사정은 존중하되, 프로젝트 약속과 일정 문제는
개인 관계와 분리해 투명하게 다룹니다. 감정으로 넘기거나 공개적으로 압박하지 않습니다.

### 2. 투명한 실행 관리

“서로 감시”가 아니라, 서로가 막히지 않도록 작업 상태와 위험을 일찍 공유하는 제도입니다.

- 주간 목표: 담당 기능의 완료 조건을 작고 명확하게 작성
- 진행 공유: 작업 시작/진행/막힘/완료를 Discord 또는 GitHub에서 공개
- 짧은 데모: 완료 주장보다 실제 실행 화면·PR·테스트 결과로 확인
- 상호 리뷰: 코드/기획/밸런스를 최소 1명 이상이 확인
- 블로커 우선 공유: 늦기 전에 도움을 요청하는 것을 좋은 협업으로 평가

### 3. 상시 리뷰와 질문 문화

리뷰는 잘못을 찾는 평가가 아니라, 팀이 같은 방향을 이해하고 더 나은 결정을 내리기 위한 장치입니다.
실력이나 경험과 관계없이 누구나 구현·기획·설계에 대한 의문과 호기심을 제시할 수 있어야 합니다.

- 코드, 기획, 데이터, UI 흐름, 기술 선택을 상시 리뷰 대상으로 둡니다.
- 이해되지 않는 구현이나 방향은 질문하고, 구현자는 의도·대안·트레이드오프를 설명합니다.
- 한 사람이 다른 팀원이 따라갈 수 없는 방향으로 독주하지 않도록, 핵심 결정은 문서와 리뷰로 공유합니다.
- "왜 이렇게 만들었는가"를 설명할 수 있는 것을 완료 기준의 일부로 봅니다.

### 4. 스터디와 성장 루틴

중간 규모 게임을 만들기 위해 시스템 설계, 밸런싱, 재화 경제, 데이터 저장, Steam/온라인,
테스트를 함께 학습합니다. 스터디는 보여주기용이 아니라 현재 작업에 즉시 적용하는 방식입니다.

- 1~2주 단위 주제 선정: 예) ScriptableObject 밸런싱, Profile 저장, Unity 테스트, Netcode 권한
- 짧은 자료 공유 + 각자 핵심 요약
- 프로젝트 코드/기획에 적용할 작은 실험 또는 개선안 제출
- 학습 결과는 팀 문서와 실제 작업 항목으로 남김

### 5. 유지보수 가능한 설계와 높은 책임 기준

이 프로젝트는 취미성 아이디어 공유방이 아니라 출시를 목표로 하는 개발 팀입니다.

빠른 구현 자체보다, 이후 기능 추가·온라인 확장·버그 수정이 가능한 합리적인 설계와 이를 뒷받침하는
기반 지식을 중요하게 봅니다. 작업은 동작 여부만이 아니라 책임 분리, 데이터 흐름, 테스트 가능성,
문서화, 리뷰 가능성을 함께 고려해야 합니다.

- 합의한 코어 타임과 담당 작업을 지킵니다.
- 일정이 어려우면 마감 전에 알리고, 범위 조정 또는 인수인계를 제안합니다.
- 반복적인 무응답, 약속 불이행, 협업 방해, 학습/작업 의지 부재는 명확한 피드백 대상입니다.
- 피드백 뒤에도 개선 의지나 실행이 없으면 팀과 프로젝트의 건강을 위해 참여를 종료할 수 있습니다.

기준은 사람을 압박하기 위한 것이 아니라, 성실하게 기여하는 팀원의 시간과 신뢰를 보호하기 위한 것입니다.

### 6. AI 활용 원칙

AI는 코드, 문서, 리서치, 테스트의 생산성을 높이는 보조 도구로 적극 활용합니다. 다만 AI가 생성한
결과를 그대로 제출하거나 이해하지 못한 코드를 팀 코드로 넣는 것은 허용하지 않습니다.

- 구현자는 자신이 작성하거나 AI 도움을 받아 작성한 코드의 동작, 의존성, 한계, 테스트 방법을 설명할 수 있어야 합니다.
- AI 결과는 코드 리뷰와 실행/테스트를 통해 검증합니다.
- 라이선스, 저작권, 보안, 개인정보, 외부 API 키 등은 AI 출력이라도 구현자가 책임지고 확인합니다.
- AI 사용 사실을 숨길 필요는 없으며, 좋은 프롬프트·검증 방법·학습 결과를 팀에 공유합니다.
